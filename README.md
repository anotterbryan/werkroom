# RPDR Tracking

A relational database of **RuPaul's Drag Race** (US main series, all 18 aired seasons)
and an original, copyright-safe data-visualization website built from it.

The data lives as ten linked CSV tables in [`data/`](data/) — the single source of truth.
A small, dependency-light build pipeline compiles those CSVs into the artifacts the
website and spreadsheet consume. Everything is reproducible: edit a CSV, run the build,
get an updated site.

## What's here

```

data/                 10 source-of-truth CSV tables (queens, seasons, contestants,
                      episodes, progression, songs, lip_syncs, elimination_events,
                      panel, appearances)
scripts/
  build_site_data.py  data/*.csv  -> site/site_data.js   (regenerate after data edits)
  build_xlsx.py       data/*.csv  -> dist/DragRaceDB_master.xlsx
  validate.py         invariant suite (CI gate)
site/
  index.html          the website: all HTML/CSS + 31 view functions (EDIT THIS for views)
  site_data.js        generated data the site loads (regenerated by build_site_data.py)
  index.embedded.html frozen standalone snapshot (data baked in) — offline fallback only
docs/
  DATA_MODEL.md       schema + data dictionary for all tables and derived views
  CONVENTIONS.md      the ground rules (no guessing, `-` for unknowns, etc.)
  HANDOFF.md          current state and roadmap
.github/workflows/    CI: validate on every push; build + deploy to Pages
```

## Quick start

```bash
pip install -r requirements.txt          # only openpyxl, for the spreadsheet

python scripts/validate.py               # check data integrity (exits non-zero on error)
python scripts/build_site_data.py        # data/*.csv -> site/site_data.js
python scripts/build_xlsx.py             # -> dist/DragRaceDB_master.xlsx
```

To preview locally, serve the `site/` folder (browsers block a file:// page from loading
its data file): `cd site && python3 -m http.server`, then open http://localhost:8000.
On GitHub Pages it just works. (The frozen `site/index.embedded.html` has its data baked
in, so that one *can* be opened by double-clicking — handy as an offline copy.)

## How the build is decoupled (important)

The website's view code and the data are kept in **separate files**:

- `site/index.html` holds all HTML, CSS, and the 31 view-render functions. It loads its
  data at the top with `<script src="site_data.js"></script>`, which defines a global
  `DATA` object the views read.
- `scripts/build_site_data.py` regenerates `site/site_data.js` from the CSVs.

So editing data only rewrites `site_data.js`, and **a data rebuild never touches
`index.html` or your views.** Edit `index.html` for anything visual; run the build for
anything data. (There's no template or inject step — `index.html` is the real file you
edit.)

## The golden rule

`episodes.eliminated_id` is authoritative for who went home, and the win/high/low/bottom
tallies are **computed** from the `progression` grid — never hand-typed. `validate.py`
enforces both, plus referential integrity, on every change. Never invent data: unknown
values are left as `-`. See [`docs/CONVENTIONS.md`](docs/CONVENTIONS.md).

## Deploying to GitHub Pages

Two options (see [`.github/workflows/pages.yml`](.github/workflows/pages.yml)):

1. **Actions build (recommended):** the workflow runs the build and publishes `site/`.
2. **Serve the folder:** in repo Settings → Pages, serve from the `main` branch `/site`
   folder. Since `site/index.html` is committed, this works with no build step.
